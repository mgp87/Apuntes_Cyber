# Networking — Resumen para Pentesting

> Este resumen cubre los conceptos de networking más importantes para entender cómo se comunican los sistemas, cómo se encapsula el tráfico y qué protocolos suelen aparecer durante reconocimiento, análisis de servicios y pentesting.

---

# 1. OSI Model

El modelo **OSI — Open Systems Interconnection** divide la comunicación de red en **7 capas**.

```text
┌─────────────────────────────┐
│ 7. Application             │
├─────────────────────────────┤
│ 6. Presentation            │
├─────────────────────────────┤
│ 5. Session                 │
├─────────────────────────────┤
│ 4. Transport               │
├─────────────────────────────┤
│ 3. Network                 │
├─────────────────────────────┤
│ 2. Data Link               │
├─────────────────────────────┤
│ 1. Physical                │
└─────────────────────────────┘
```

## Las 7 capas

|Capa|Nombre|Función|Ejemplos|
|--:|---|---|---|
|**7**|Application|Servicios utilizados por las aplicaciones|HTTP, SMTP, FTP, SSH, DNS|
|**6**|Presentation|Formato, codificación, cifrado|TLS, JSON, JPEG, UTF-8|
|**5**|Session|Gestión de sesiones|RPC, NetBIOS Session|
|**4**|Transport|Comunicación entre procesos|TCP, UDP|
|**3**|Network|Direccionamiento y routing|IPv4, IPv6, ICMP|
|**2**|Data Link|Comunicación dentro de la LAN|Ethernet, MAC, ARP*|
|**1**|Physical|Transmisión física|Cable, fibra, radio|

> ARP suele describirse como un protocolo situado entre las capas 2 y 3 porque relaciona direcciones IPv4 con direcciones MAC.

---

## Unidad de datos por capa

```text
Application
    ↓
Data
    ↓
Transport
    ↓
TCP Segment / UDP Datagram
    ↓
Network
    ↓
IP Packet
    ↓
Data Link
    ↓
Ethernet Frame
    ↓
Physical
    ↓
Bits
```

---

## Ejemplo

Al solicitar:

```text
https://example.com
```

pueden participar:

```text
HTTP                → Layer 7
TLS                 → Layers 5-6 aproximadamente
TCP                 → Layer 4
IP                  → Layer 3
Ethernet            → Layer 2
Cable / Wi-Fi       → Layer 1
```

---

# 2. TCP/IP Model

El modelo TCP/IP es el utilizado de forma práctica en Internet.

Tiene normalmente **4 capas**:

```text
┌─────────────────────────────┐
│ Application                 │
├─────────────────────────────┤
│ Transport                   │
├─────────────────────────────┤
│ Internet                    │
├─────────────────────────────┤
│ Network Access              │
└─────────────────────────────┘
```

## Correspondencia OSI ↔ TCP/IP

|OSI|TCP/IP|
|---|---|
|7 Application|Application|
|6 Presentation|Application|
|5 Session|Application|
|4 Transport|Transport|
|3 Network|Internet|
|2 Data Link|Network Access|
|1 Physical|Network Access|

---

## Protocolos típicos

```text

├── SMTP
├── IMAP

Transport
├── TCP
└── UDP

Internet
├── IPv4
├── IPv6
└── ICMP

Network Access
├── Ethernet
├── Wi-Fi
└── ARP
```

# 3. IP Addresses and Subnets

Una dirección IP identifica una interfaz dentro de una red IP.

## IPv4

Tiene **32 bits**:

```text
192.168.1.10
```

Representación binaria:

```text
192      168       1       10

11000000.10101000.00000001.00001010
```

Cada bloque contiene 8 bits:

```text
8 + 8 + 8 + 8 = 32 bits
```

---

# CIDR

Una red suele representarse:

```text
192.168.1.0/24
```

El `/24` indica:

```text
24 bits → parte de red
8 bits  → hosts
```

Máscara:

```text
255.255.255.0
```

---

# Ejemplo `/24`

```text
Red:
192.168.1.0/24

Network address:
192.168.1.0

Hosts:
192.168.1.1
...
192.168.1.254

Broadcast:
192.168.1.255
```

Número total de direcciones:

```text
2^(32-prefix)
```

Para `/24`:

```text
2^(32-24)
=
2^8
=
256
```

En una subred IPv4 tradicional:

```text
hosts utilizables ≈ 2^hostbits - 2
```

porque se reservan normalmente:

- network address;
    
- broadcast address.
    

> Hay excepciones modernas, como redes `/31` punto a punto.

---

# Máscaras frecuentes

|CIDR|Máscara|Direcciones|Hosts tradicionales|
|---|---|--:|--:|
|`/8`|`255.0.0.0`|16.777.216|16.777.214|
|`/16`|`255.255.0.0`|65.536|65.534|
|`/24`|`255.255.255.0`|256|254|
|`/25`|`255.255.255.128`|128|126|
|`/26`|`255.255.255.192`|64|62|
|`/27`|`255.255.255.224`|32|30|
|`/28`|`255.255.255.240`|16|14|
|`/29`|`255.255.255.248`|8|6|
|`/30`|`255.255.255.252`|4|2|

---

# Rangos IPv4 privados

No son directamente enroutables por Internet.

|Rango|CIDR|
|---|---|
|`10.0.0.0 – 10.255.255.255`|`10.0.0.0/8`|
|`172.16.0.0 – 172.31.255.255`|`172.16.0.0/12`|
|`192.168.0.0 – 192.168.255.255`|`192.168.0.0/16`|

---

# Otras direcciones importantes

## Loopback

```text
127.0.0.1
```

Habitualmente:

```text
localhost
```

Todo el rango:

```text
127.0.0.0/8
```

---

## APIPA / Link-local

```text
169.254.0.0/16
```

Puede aparecer cuando un host no consigue una configuración IPv4 mediante DHCP.

---

## Broadcast limitado

```text
255.255.255.255
```

---

# IPv6

IPv6 utiliza **128 bits**.

Ejemplo:

```text
2001:db8:1234:5678::10
```

Loopback:

```text
::1
```

Link-local:

```text
fe80::/10
```

IPv6 no utiliza ARP; utiliza **Neighbor Discovery Protocol — NDP**, basado en ICMPv6.

# 4. UDP y TCP

TCP y UDP pertenecen a la **capa de transporte**.

---

# TCP

**Transmission Control Protocol**

Orientado a conexión.

Características:

- fiable;
    
- mantiene estado;
    
- controla el orden;
    
- retransmite datos perdidos;
    
- utiliza acknowledgements;
    
- control de flujo;
    
- control de congestión.
    

---

## TCP Three-Way Handshake

Para crear una conexión:

```text
Client                   Server
   │                        │
   │──── SYN ──────────────>│
   │                        │
   │<── SYN + ACK ──────────│
   │                        │
   │──── ACK ──────────────>│
   │                        │
   │   CONNECTION ESTABLISHED
```

Simplificado:

```text
SYN
SYN-ACK
ACK
```

---

## Flags TCP importantes

|Flag|Significado|
|---|---|
|`SYN`|Iniciar/sincronizar conexión|
|`ACK`|Confirmación|
|`FIN`|Finalización ordenada|
|`RST`|Reset inmediato|
|`PSH`|Entregar datos a aplicación|
|`URG`|Datos urgentes|

---

# UDP

**User Datagram Protocol**

No establece una conexión previa.

```text
Client ───── Datagram ─────> Server
```

Características:

- sin handshake;
    
- sin retransmisión propia;
    
- no garantiza entrega;
    
- no garantiza orden;
    
- menor overhead;
    
- muy rápido.
    

---

# TCP vs UDP

|Característica|TCP|UDP|
|---|---|---|
|Orientado a conexión|Sí|No|
|Fiable|Sí|No por sí mismo|
|Orden garantizado|Sí|No|
|Retransmisión|Sí|No|
|Overhead|Mayor|Menor|
|Velocidad/latencia|Más coste|Menos coste|
|Estado|Stateful|Connectionless|

Ejemplos típicos:

```text
TCP
├── HTTP/1.1
├── HTTP/2
├── SSH
├── SMTP
├── FTP
└── IMAP

UDP
├── DHCP
├── DNS frecuentemente
├── VoIP
└── streaming/tiempo real
```

> HTTP/3 utiliza QUIC sobre UDP.

---

# 5. Encapsulation

La encapsulación ocurre cuando cada capa añade su propia información antes de transmitir los datos.

Ejemplo HTTP:

```text
HTTP data
    ↓
TCP Header + HTTP data
    ↓
IP Header + TCP Segment
    ↓
Ethernet Header + IP Packet + Ethernet Trailer
    ↓
Bits
```

Visualmente:

```text
┌────────────────────────────────────────────┐
│ Ethernet Header                            │
│   ┌────────────────────────────────────┐   │
│   │ IP Header                          │   │
│   │   ┌────────────────────────────┐   │   │
│   │   │ TCP Header                 │   │   │
│   │   │   ┌────────────────────┐   │   │   │
│   │   │   │ HTTP Data          │   │   │   │
│   │   │   └────────────────────┘   │   │   │
│   │   └────────────────────────────┘   │   │
│   └────────────────────────────────────┘   │
│ Ethernet Trailer                           │
└────────────────────────────────────────────┘
```

En el receptor ocurre lo contrario:

```text
Decapsulation
```

---

# Direcciones utilizadas durante la encapsulación

```text
Layer 2
MAC source → MAC destination

Layer 3
IP source → IP destination

Layer 4
Source port → Destination port
```

Ejemplo:

```text
MAC:
AA:AA:AA:AA:AA:AA
      ↓
BB:BB:BB:BB:BB:BB

IP:
192.168.1.20
      ↓
93.184.216.34

TCP:
49152
 ↓
443
```

# 6. Telnet

**Telnet** proporciona acceso remoto mediante terminal.

Puerto habitual:

```text
TCP/23
```

Ejemplo:

```bash
telnet 192.168.1.10 23
```

Problema fundamental:

> Telnet transmite la información **sin cifrar**.

Esto puede incluir:

- usuario;
    
- contraseña;
    
- comandos;
    
- respuestas.
    

Por eso ha sido sustituido prácticamente por **SSH**.

---

## Uso como cliente TCP básico

`telnet` también puede utilizarse para probar manualmente servicios TCP:

```bash
telnet servidor 80
```

Por ejemplo, para comprobar si existe conectividad TCP hacia un puerto.

---

# 7. DHCP

**Dynamic Host Configuration Protocol**

Permite configurar automáticamente hosts dentro de una red.

Puede proporcionar:

- dirección IP;
    
- máscara;
    
- gateway;
    
- DNS;
    
- duración del lease;
    
- otras opciones de red.
    

Puertos:

```text
UDP/67 → DHCP Server
UDP/68 → DHCP Client
```

---

# DORA

Proceso típico:

```text
Discover
   ↓
Offer
   ↓
Request
   ↓
Acknowledge
```

## 1. DHCP Discover

El cliente busca servidores DHCP.

```text
Client → Broadcast
```

## 2. DHCP Offer

El servidor ofrece una configuración.

```text
Server → Client
```

## 3. DHCP Request

El cliente solicita utilizar la configuración ofrecida.

## 4. DHCP ACK

El servidor confirma el lease.

---

# Flujo

```text
Client                      DHCP Server

 DHCP Discover
───────────────────────────>

       DHCP Offer
<───────────────────────────

 DHCP Request
───────────────────────────>

       DHCP ACK
<───────────────────────────
```

---

# 8. ARP — Bridging Layer 3 Addressing to Layer 2 Addressing

**ARP — Address Resolution Protocol**

Permite relacionar:

```text
IPv4 address
     ↓
MAC address
```

Ejemplo:

```text
192.168.1.1
       ↓
AA:BB:CC:DD:EE:FF
```

---

# Problema que resuelve

Un equipo quiere enviar un paquete a:

```text
192.168.1.20
```

Conoce la IP, pero Ethernet necesita una **dirección MAC**.

Por tanto pregunta:

```text
Who has 192.168.1.20?
```

---

# ARP Request

Se envía mediante broadcast:

```text
FF:FF:FF:FF:FF:FF
```

Conceptualmente:

```text
¿Quién tiene 192.168.1.20?
```

---

# ARP Reply

El propietario responde:

```text
192.168.1.20 is at
AA:BB:CC:DD:EE:FF
```

---

# ARP Cache

Los hosts guardan temporalmente estas asociaciones.

Linux:

```bash
ip neigh
```

También históricamente:

```bash
arp -a
```

Ejemplo:

```text
192.168.1.1 dev eth0 lladdr AA:BB:CC:DD:EE:FF REACHABLE
```

---

# Importante

ARP funciona únicamente dentro del dominio de broadcast local.

Si el destino está en otra red:

```text
Host
 ↓
ARP para conocer MAC del gateway
 ↓
Router
 ↓
Ruta hacia destino
```

El host **no busca directamente la MAC del servidor remoto**.

---

# 9. ICMP

**Internet Control Message Protocol**

Se utiliza para enviar información de control, diagnóstico y errores relacionados con IP.

No utiliza puertos TCP/UDP.

---

# `ping`

Utiliza normalmente:

```text
ICMP Echo Request
ICMP Echo Reply
```

Ejemplo:

```bash
ping 192.168.1.1
```

Flujo:

```text
Echo Request
────────────>

Echo Reply
<────────────
```

---

# Mensajes ICMP importantes

|Mensaje|Función|
|---|---|
|Echo Request|Solicitud ping|
|Echo Reply|Respuesta ping|
|Destination Unreachable|Destino inaccesible|
|Time Exceeded|TTL agotado|
|Redirect|Indicar una ruta alternativa|

---

# TTL

Cada router reduce el **Time To Live** del paquete.

```text
TTL 64
 ↓ router
TTL 63
 ↓ router
TTL 62
```

Cuando llega a:

```text
TTL = 0
```

el router descarta el paquete y puede enviar:

```text
ICMP Time Exceeded
```

Este comportamiento es la base de herramientas como:

```bash
traceroute
```

---

# 10. Routing

Routing determina por dónde debe enviarse un paquete para alcanzar otra red.

Un router conecta diferentes redes IP.

Ejemplo:

```text
192.168.1.0/24
       │
       │
   192.168.1.1
     ROUTER
   10.0.0.1
       │
       │
10.0.0.0/24
```

---

# Routing table

Linux:

```bash
ip route
```

Ejemplo:

```text
default via 192.168.1.1 dev eth0

192.168.1.0/24 dev eth0
```

---

# Default Gateway

Cuando un host quiere alcanzar una red que no conoce directamente:

```text
Host
 ↓
Default Gateway
 ↓
Router(s)
 ↓
Destination
```

Ejemplo:

```text
default via 192.168.1.1
```

---

# Longest Prefix Match

Si existen varias rutas, normalmente se elige la más específica.

Ejemplo:

```text
10.0.0.0/8
10.10.0.0/16
10.10.20.0/24
```

Para:

```text
10.10.20.50
```

se utilizaría:

```text
10.10.20.0/24
```

porque es la ruta más específica.

---

# Routing estático

Configurado manualmente.

Ejemplo Linux:

```bash
ip route add 10.20.0.0/16 via 192.168.1.1
```

---

# Routing dinámico

Los routers intercambian información automáticamente mediante protocolos como:

- OSPF;
    
- BGP;
    
- IS-IS;
    
- RIP.
    

---

# 11. NAT

**Network Address Translation**

Modifica direcciones IP al atravesar un dispositivo como un router o firewall.

Ejemplo típico:

```text
LAN

192.168.1.20
192.168.1.21
192.168.1.22
       │
       ▼
     Router
203.0.113.10
       │
       ▼
    Internet
```

Varios dispositivos privados pueden compartir una sola IP pública.

---

# SNAT

**Source NAT**

Modifica la dirección origen.

```text
192.168.1.20
      ↓
203.0.113.10
```

Muy habitual en conexiones de salida hacia Internet.

---

# DNAT

**Destination NAT**

Modifica la dirección de destino.

Puede utilizarse para publicar servicios internos.

```text
203.0.113.10:443
       ↓
192.168.1.50:443
```

---

# PAT / NAT Overload

También modifica puertos.

Ejemplo:

```text
192.168.1.20:50000
       ↓
203.0.113.10:60001
```

y:

```text
192.168.1.21:50000
       ↓
203.0.113.10:60002
```

Así múltiples conexiones comparten una IP pública.

---

# NAT no es un firewall

Aunque NAT puede dificultar conexiones entrantes directas, conceptualmente:

```text
NAT
=
traducción de direcciones

Firewall
=
control del tráfico
```

Son funciones diferentes.

# 13. HTTP

**Hypertext Transfer Protocol**

Protocolo utilizado principalmente para comunicaciones web.

Puerto habitual:

```text

```

---


---

# 14. FTP

**File Transfer Protocol**

Utilizado para transferencia de archivos.

Puerto de control:

```text
TCP/21
```

FTP clásico transmite credenciales y datos **sin cifrar**.

---

# Dos conexiones

FTP utiliza una conexión de control y otra de datos.

```text
Control:
TCP/21

Data:
depende de Active / Passive mode
```

---

# Active FTP

Tradicionalmente:

```text
Client ── TCP/21 ──> Server
Client <── TCP/20 ── Server
```

El servidor inicia la conexión de datos hacia el cliente.

---

# Passive FTP

El servidor abre un puerto dinámico y el cliente conecta hacia él.

```text
Client
  │
  ├── TCP/21 ──────> Server
  │
  └── dynamic port → Server
```

Es más compatible con NAT y firewalls.

---

# 15. SMTP

**Simple Mail Transfer Protocol**

Se utiliza para enviar y retransmitir correo electrónico.

Puertos importantes:

|Puerto|Uso|
|--:|---|
|`25/TCP`|SMTP entre servidores|
|`587/TCP`|Mail Submission|
|`465/TCP`|SMTP con TLS implícito|

---

# Flujo simplificado

```text
Mail Client
     ↓
SMTP Submission
     ↓
Mail Server
     ↓
SMTP
     ↓
Destination Mail Server
```

SMTP sirve principalmente para **enviar** correo.

Para recuperarlo suelen utilizarse:

```text
POP3
IMAP
```

---

# Comandos SMTP clásicos

Conceptualmente:

```text
EHLO
MAIL FROM
RCPT TO
DATA
QUIT
```

# 16. POP3

**Post Office Protocol version 3**

Permite descargar correo desde un servidor.

Puerto:

```text
TCP/110
```

Con TLS implícito:

```text
TCP/995
```

Modelo tradicional:

```text
Mail Server
    ↓
Download
    ↓
Mail Client
```

POP3 está orientado principalmente a descargar mensajes.

---

# 17. IMAP

**Internet Message Access Protocol**

Permite gestionar el correo manteniéndolo en el servidor.

Puerto:

```text
TCP/143
```

IMAPS:

```text
TCP/993
```

---

# POP3 vs IMAP

|POP3|IMAP|
|---|---|
|Diseñado principalmente para descarga|Trabaja principalmente contra el servidor|
|Modelo sencillo|Sincronización|
|Menor funcionalidad|Carpetas, flags, estados|
|Menos adecuado para múltiples dispositivos|Excelente para múltiples dispositivos|

# 18. TLS

**Transport Layer Security**

Proporciona seguridad criptográfica para protocolos de aplicación.

Puede proporcionar:

```text
Confidentiality
+
Integrity
+
Authentication
```

Es decir:

- cifrado;
    
- detección de modificaciones;
    
- autenticación, normalmente del servidor mediante certificados.
    

---

# TLS no es HTTPS

TLS es una capa de seguridad que puede proteger diferentes protocolos.

```text
HTTP + TLS
=
HTTPS
```

También:

```text
SMTP + TLS
IMAP + TLS
POP3 + TLS
FTP + TLS
```

---

# TLS Handshake simplificado

```text
Client
  │
  │── ClientHello ─────────────>
  │
  │<─ ServerHello + Certificate
  │
  │   negociación criptográfica
  │
  │   establecimiento de claves
  │
  │<════════ encrypted ════════>
```

Durante el proceso se negocian aspectos como:

- versión TLS;
    
- algoritmos;
    
- parámetros criptográficos;
    
- claves de sesión.
    

---

# Certificados

El servidor suele presentar un certificado X.509.

Incluye información como:

- dominio;
    
- clave pública;
    
- emisor;
    
- fechas de validez;
    
- firma;
    
- Subject Alternative Names.
    

La confianza normalmente sigue:

```text
Root CA
   ↓
Intermediate CA
   ↓
Server Certificate
```

# 19. HTTPS

# 12.1. RDAP — Replacement for WHOIS

**RDAP — Registration Data Access Protocol** es el protocolo moderno diseñado para sustituir progresivamente a **WHOIS** en consultas de información de registro de:

- dominios;
    
- direcciones IPv4/IPv6;
    
- ASN;
    
- registradores;
    
- entidades/contactos cuando la política permite mostrarlos.
    

La idea general es:

```text
WHOIS
   ↓
Protocolo antiguo basado en texto
   ↓
RDAP
   ↓
HTTP(S) + JSON + datos estructurados
```

---

# ¿Por qué sustituir WHOIS?

WHOIS tiene varias limitaciones:
- salida de texto sin formato estándar;
- cada servidor puede responder de manera diferente;
- difícil de procesar automáticamente;
- soporte limitado de internacionalización;
- mecanismos poco estandarizados para redirecciones;
- no proporciona de forma nativa una API web estructurada;
- históricamente utiliza conexiones sin cifrar.

RDAP soluciona gran parte de estos problemas.

---

# WHOIS vs RDAP

|Característica|WHOIS|RDAP|
|---|---|---|
|Formato|Texto libre|**JSON estructurado**|
|Transporte|TCP|**HTTP/HTTPS**|
|Puerto habitual|`43/TCP`|`443/TCP` normalmente|
|Cifrado|No por defecto|**HTTPS**|
|API REST-like|❌|✅|
|Respuestas estandarizadas|Limitadas|✅|
|Internacionalización|Limitada|Mejor soporte|
|Redirecciones|No estandarizadas|✅|
|Procesamiento automático|Más difícil|✅|
|Status HTTP|❌|✅|
|Autenticación extensible|Muy limitada|✅|
|Sustituto moderno|❌|**✅**|

---

# Cómo funciona RDAP

Una consulta RDAP utiliza normalmente HTTPS.

Ejemplo conceptual:

```text
Client
   │
   │ HTTPS GET
   ▼
RDAP Server
   │
   │ JSON
   ▼
Client
```

En lugar de recibir:

```text
Domain Name: EXAMPLE.COM
Registrar: Example Registrar
Creation Date: ...
```

como texto plano, RDAP devuelve información estructurada parecida a:

```json
{
  "objectClassName": "domain",
  "ldhName": "example.com",
  "status": [
    "active"
  ],
  "events": [
    {
      "eventAction": "registration",
      "eventDate": "..."
    }
  ]
}
```

Esto facilita enormemente el procesamiento automático.


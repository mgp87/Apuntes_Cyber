# Passive Reconnaissance — `dig`, `nslookup`, Shodan, crt.sh y DNSDumpster

> **Passive Reconnaissance** consiste en recopilar información sobre un objetivo utilizando fuentes públicas o servicios de terceros, intentando **no interactuar directamente con los sistemas del objetivo**.

```text
Target
   │
   ├── DNS
   ├── Certificate Transparency
   ├── Search Engines
   ├── Internet Scanners
   └── Public Databases
          │
          ▼
 Passive Reconnaissance
```

Ejemplos habituales:

```text
RDAP
WHOIS
DNS
crt.sh
Shodan
DNSDumpster
Search engines
Public repositories
```

---

# `dig`

`dig` significa **Domain Information Groper**.

Es una herramienta de línea de comandos utilizada para realizar consultas DNS.

Permite consultar registros como:

```text
A
AAAA
MX
NS
TXT
CNAME
SOA
PTR
```

Sintaxis básica:

```bash
dig example.com
```

---

# Consultar un registro `A`

Devuelve direcciones IPv4:

```bash
dig example.com A
```

Respuesta simplificada:

```text
example.com.    300    IN    A    93.184.216.34
```

---

# Consultar IPv6

Registro:

```text
AAAA
```

Comando:

```bash
dig example.com AAAA
```

---

# Consultar servidores DNS

```bash
dig example.com NS
```

Ejemplo:

```text
example.com.    IN    NS    ns1.example.net.
example.com.    IN    NS    ns2.example.net.
```

---

# Consultar servidores de correo

```bash
dig example.com MX
```

Ejemplo:

```text
example.com.    IN    MX    10 mail.example.com.
```

El número:

```text
10
```

representa la prioridad.

Generalmente:

```text
menor número
=
mayor prioridad
```

---

# Consultar registros TXT

```bash
dig example.com TXT
```

Los TXT pueden contener información relacionada con:

- SPF;
    
- DKIM;
    
- DMARC;
    
- verificaciones de dominio;
    
- proveedores cloud;
    
- servicios SaaS.
    

---

# Consultar CNAME

```bash
dig www.example.com CNAME
```

Un CNAME representa un alias:

```text
www.example.com
        ↓
web.example.net
```

---

# Consultar SOA

```bash
dig example.com SOA
```

**SOA — Start of Authority** contiene información administrativa sobre la zona DNS.

Puede incluir:

- servidor DNS principal;
    
- contacto administrativo codificado;
    
- serial;
    
- tiempos de refresh;
    
- retry;
    
- expire.
    

---

# Consultas inversas

Permiten obtener un nombre asociado a una IP mediante registros PTR.

```bash
dig -x 8.8.8.8
```

Conceptualmente:

```text
IP
 ↓
PTR
 ↓
Hostname
```

---

# Mostrar sólo la respuesta

Muy útil:

```bash
dig example.com +short
```

Ejemplo:

```text
93.184.216.34
```

MX:

```bash
dig example.com MX +short
```

NS:

```bash
dig example.com NS +short
```

TXT:

```bash
dig example.com TXT +short
```

---

# Consultar un servidor DNS específico

```bash
dig @8.8.8.8 example.com
```

Sintaxis:

```text
@
+
DNS SERVER
```

Por ejemplo:

```bash
dig @1.1.1.1 example.com A
```

---

# Seguir la resolución DNS

```bash
dig example.com +trace
```

Permite observar la cadena desde los servidores raíz:

```text
Root Servers
      ↓
TLD Servers
      ↓
Authoritative DNS
      ↓
Record
```

Ejemplo conceptual:

```text
.
 ↓
.com
 ↓
example.com
 ↓
A record
```

---

# Flags útiles de `dig`

|Flag|Función|
|---|---|
|`+short`|Muestra sólo la respuesta|
|`+trace`|Sigue la delegación DNS|
|`+noall`|Oculta secciones|
|`+answer`|Muestra únicamente Answer|
|`+stats`|Estadísticas|
|`+tcp`|Fuerza TCP|
|`-x`|Reverse lookup|
|`@server`|Consulta un servidor concreto|

Ejemplo:

```bash
dig example.com +noall +answer
```

---

# `dig ANY`

Existe:

```bash
dig example.com ANY
```

pero actualmente suele ser **poco útil**.

Muchos servidores DNS:

- limitan las respuestas `ANY`;
    
- devuelven información parcial;
    
- responden con conjuntos mínimos.
    

Es preferible consultar específicamente:

```bash
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com NS
dig example.com TXT
dig example.com SOA
```

---

# ¿`dig` es Passive Reconnaissance?

Depende de **a quién preguntes**.

Si consultas un resolver público:

```bash
dig @1.1.1.1 example.com
```

tu consulta va inicialmente a:

```text
Cloudflare DNS
```

pero dependiendo de la caché, ese resolver puede consultar posteriormente a los DNS autoritativos del dominio.

Por tanto:

> `dig` es una herramienta de **DNS reconnaissance**, pero no debe considerarse tan estrictamente pasiva como consultar bases de datos de terceros como crt.sh o Shodan.

# `nslookup`

`nslookup` es otra herramienta para realizar consultas DNS.

Es más antigua y normalmente menos flexible que `dig`, pero está disponible en muchos sistemas, incluyendo Windows.

Uso básico:

```bash
nslookup example.com
```

Salida típica:

```text
Name:    example.com
Address: 93.184.216.34
```

---

# Consultar un tipo de registro

MX:

```bash
nslookup -type=MX example.com
```

NS:

```bash
nslookup -type=NS example.com
```

TXT:

```bash
nslookup -type=TXT example.com
```

AAAA:

```bash
nslookup -type=AAAA example.com
```

SOA:

```bash
nslookup -type=SOA example.com
```

---

# Reverse DNS

```bash
nslookup 8.8.8.8
```

Puede devolver el PTR asociado.

---

# Servidor DNS específico

```bash
nslookup example.com 1.1.1.1
```

Esto significa:

```text
Consulta example.com
usando 1.1.1.1
como DNS resolver
```

---

# Modo interactivo

Ejecutar:

```bash
nslookup
```

Después:

```text
> server 1.1.1.1
> set type=MX
> example.com
```

Cambiar tipo:

```text
> set type=TXT
```

Salir:

```text
> exit
```

---

# `dig` vs `nslookup`

|Característica|`dig`|`nslookup`|
|---|---|---|
|Consultas DNS|✅|✅|
|Linux|✅|✅|
|Windows|Puede instalarse|✅ frecuente|
|Salida detallada|✅|Más simple|
|Automatización|✅ excelente|🟡|
|`+trace`|✅|❌|
|Consultar servidor concreto|✅|✅|
|Reverse DNS|✅|✅|
|Uso profesional DNS|**Preferido**|Útil para consultas rápidas|

Regla práctica:

```text
dig
=
más potente y flexible

nslookup
=
más rápido/simple y muy disponible
```

# Shodan

**Shodan** es un motor de búsqueda especializado en dispositivos y servicios expuestos a Internet.

En lugar de indexar páginas web como Google, Shodan indexa información obtenida de servicios de red públicos.

Conceptualmente:

```text
Internet
   │
   ├── Web servers
   ├── SSH servers
   ├── VPN gateways
   ├── Routers
   ├── Firewalls
   ├── IoT
   ├── Databases
   └── Industrial systems
          │
          ▼
       Shodan
          │
          ▼
 Searchable Index
```

---

# ¿Por qué Shodan es Passive Reconnaissance?

El investigador consulta:

```text
Shodan
```

en lugar de consultar directamente:

```text
Target
```

Flujo:

```text
Pentester
    ↓
 Shodan
    ↓
Indexed historical/current observations
```

Por tanto, desde el punto de vista del pentester:

> la consulta es normalmente **pasiva respecto al objetivo**.

Shodan ya ha realizado previamente su propia recopilación de información pública.

---

# Información que puede mostrar Shodan

Dependiendo del activo:

- dirección IP;
    
- hostname;
    
- ASN;
    
- organización;
    
- geolocalización aproximada;
    
- puertos abiertos observados;
    
- banners;
    
- productos;
    
- versiones;
    
- certificados TLS;
    
- servicios expuestos;
    
- tecnologías.
    

Ejemplo conceptual:

```text
203.0.113.20

22/tcp
SSH

80/tcp
HTTP

443/tcp
HTTPS
```

---

# Búsquedas básicas

Buscar un dominio:

```text
hostname:example.com
```

Buscar organización:

```text
org:"Example Corp"
```

Buscar una red:

```text
net:203.0.113.0/24
```

Buscar puerto:

```text
port:443
```

Combinar filtros:

```text
hostname:example.com port:443
```

---

# Filtros frecuentes

|Filtro|Uso|
|---|---|
|`hostname:`|Host/domain|
|`org:`|Organización|
|`net:`|Rango/CIDR|
|`port:`|Puerto|
|`country:`|País|
|`city:`|Ciudad|
|`product:`|Producto|
|`os:`|Sistema operativo identificado|
|`ssl:`|Datos de certificados/TLS|

> La disponibilidad exacta de filtros y funcionalidades puede depender de la interfaz y del tipo de cuenta.

---

# Shodan en reconnaissance

Puede ayudar a responder:

```text
¿Qué servicios públicos conoce Shodan
para esta organización?

¿Qué puertos se han observado?

¿Qué tecnologías parecen estar desplegadas?

¿Qué certificados aparecen asociados?

¿Qué activos históricos podrían existir?
```

---

# Limitación importante

Shodan muestra datos recopilados en momentos concretos.

Por tanto:

```text
Shodan result
≠
estado necesariamente actual
```

Un puerto mostrado puede:

- haber sido cerrado;
    
- cambiar de servicio;
    
- haber cambiado de IP;
    
- proceder de un escaneo anterior.
    

Los resultados deben tratarse como:

```text
intelligence / leads
```

y no como prueba definitiva del estado actual.

# crt.sh

`crt.sh` es un buscador de **Certificate Transparency logs**.

Los Certificate Transparency Logs contienen registros públicos de certificados TLS emitidos por Certificate Authorities.

Conceptualmente:

```text
Certificate Authority
        ↓
TLS Certificate
        ↓
Certificate Transparency Log
        ↓
crt.sh
        ↓
Search
```

---

# ¿Por qué es útil?

Los certificados pueden contener:

```text
Common Name
Subject Alternative Names
```

Por ejemplo:

```text
example.com
www.example.com
api.example.com
vpn.example.com
dev.example.com
```

Esto convierte los certificados en una fuente muy útil para descubrir:

```text
subdomains
```

---

# Ejemplo de búsqueda

Buscar:

```text
example.com
```

Puede revelar:

```text
www.example.com
api.example.com
mail.example.com
vpn.example.com
staging.example.com
```

---

# Wildcard

Una consulta típica utiliza:

```text
%.example.com
```

Conceptualmente:

```text
cualquier subdominio
de
example.com
```

---

# Uso con navegador

Flujo:

```text
Domain
   ↓
crt.sh
   ↓
Certificates
   ↓
SAN / CN
   ↓
Subdomains
```

---

# Uso desde terminal

Las respuestas de crt.sh pueden consultarse en formato JSON.

Ejemplo conceptual con `curl`:

```bash
curl -s 'https://crt.sh/?q=%25.example.com&output=json'
```

Con `jq`:

```bash
curl -s 'https://crt.sh/?q=%25.example.com&output=json' | jq
```

Extraer nombres:

```bash
curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
| jq -r '.[].name_value'
```

Posteriormente pueden normalizarse:

```bash
curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
| jq -r '.[].name_value' \
| sort -u
```

---

# ¿Por qué crt.sh es Passive Reconnaissance?

Porque se consulta:

```text
Certificate Transparency Logs
```

en lugar de consultar directamente:

```text
target servers
```

Flujo:

```text
Pentester
     ↓
crt.sh
     ↓
Public CT logs
```

Por tanto, es una fuente clásica de **passive subdomain enumeration**.

---

# Limitaciones de crt.sh

Los nombres encontrados pueden corresponder a:

- sistemas actuales;
    
- sistemas retirados;
    
- entornos antiguos;
    
- certificados expirados;
    
- infraestructura migrada;
    
- nombres que ya no resuelven.
    

Por tanto:

```text
Certificate found
≠
host currently alive
```

# DNSDumpster

**DNSDumpster** es un servicio de reconnaissance DNS que agrega y correlaciona información públicamente disponible sobre un dominio.

Puede resultar útil para construir una primera imagen de:

```text
Domain
  │
  ├── Hosts
  ├── DNS records
  ├── MX
  ├── NS
  ├── IP addresses
  ├── ASN
  └── Network relationships
```

---

# Información habitual

Dependiendo del dominio puede mostrar:

- subdominios;
    
- registros DNS;
    
- direcciones IP;
    
- servidores MX;
    
- servidores NS;
    
- ASN;
    
- proveedores de hosting;
    
- mapas de relaciones.
    

---

# Ejemplo conceptual

Consulta:

```text
example.com
```

Resultado:

```text
example.com
│
├── www.example.com
│      └── 203.0.113.10
│
├── mail.example.com
│      └── 203.0.113.20
│
├── vpn.example.com
│      └── 198.51.100.10
│
├── MX
│      └── mail.example.com
│
└── NS
       ├── ns1.provider.net
       └── ns2.provider.net
```

---

# ¿Por qué DNSDumpster se utiliza para Passive Reconnaissance?

El pentester consulta:

```text
DNSDumpster
```

que agrega información procedente de diversas fuentes.

Conceptualmente:

```text
Pentester
     ↓
DNSDumpster
     ↓
Public / indexed DNS intelligence
```

Esto permite recopilar información sin iniciar directamente un escaneo de puertos contra el objetivo.

---

# Posibles usos

DNSDumpster puede ayudar a identificar:

```text
Domain
   ↓
Subdomains
   ↓
IP addresses
   ↓
Hosting provider
   ↓
ASN
   ↓
Potential infrastructure
```

Puede ser especialmente interesante para visualizar relaciones que de otra manera habría que correlacionar manualmente.

---

# Limitaciones

Los datos pueden ser:

- incompletos;
    
- históricos;
    
- desactualizados;
    
- procedentes de diferentes fuentes;
    
- afectados por CDN o reverse proxies.
    

Por ejemplo:

```text
www.example.com
      ↓
Cloudflare IP
```

no implica necesariamente que esa IP pertenezca a la organización.

---

# Passive vs Active Reconnaissance

## Passive Reconnaissance

No se interactúa directamente —o se intenta minimizar la interacción— con los sistemas del objetivo.

Ejemplos:

```text
RDAP
WHOIS
crt.sh
Shodan
DNSDumpster
Search engines
Public Git repositories
Public documents
```

Flujo:

```text
Pentester
     ↓
Third-party service
     ↓
Public information
```

---

# Active Reconnaissance

Existe interacción directa con infraestructura del objetivo.

Ejemplos conceptuales:

```text
Target
  ↑
DNS requests
HTTP requests
Port scans
Service probing
```

Por ejemplo:

```bash
curl https://target.example
```

contacta directamente con el servidor.

---

# Clasificación aproximada de las herramientas

|Herramienta|Principal función|Passive|Active|
|---|---|:-:|:-:|
|RDAP|Registration data|✅|❌|
|WHOIS|Registration data|✅|❌|
|crt.sh|Certificate Transparency|✅|❌|
|Shodan|Internet service intelligence|✅|❌|
|DNSDumpster|DNS intelligence|✅|❌|
|`dig`|DNS queries|🟡|🟡|
|`nslookup`|DNS queries|🟡|🟡|
|`curl` contra objetivo|HTTP|❌|✅|
|Port scan|Service discovery|❌|✅|

> `dig` y `nslookup` quedan en una zona intermedia: pueden consultar resolvers públicos, pero la resolución puede terminar generando consultas hacia infraestructura DNS autoritativa del dominio.

# Ejemplo de correlación

Supongamos que crt.sh muestra:

```text
vpn.example.com
```

Shodan muestra:

```text
203.0.113.50
443/tcp
```

DNSDumpster relaciona:

```text
vpn.example.com
      ↓
203.0.113.50
```

y RDAP indica:

```text
203.0.113.0/24
      ↓
Example Corporation
```

La correlación sería:

```text
crt.sh
   │
   └── vpn.example.com
              │
              ▼
        DNSDumpster
              │
              └── 203.0.113.50
                       │
              ┌────────┴────────┐
              ▼                 ▼
           Shodan              RDAP
              │                 │
           443/tcp          Organization
              │                 │
              └────────┬────────┘
                       ▼
              Candidate Asset
```

> Ninguna fuente aislada debería considerarse prueba definitiva de propiedad o estado actual. La confianza aumenta al **correlacionar varias fuentes independientes**.

# Resumen final

```text
PASSIVE RECONNAISSANCE

                TARGET DOMAIN
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
      RDAP         crt.sh       Shodan
        │            │            │
   Ownership     Subdomains    Services
   / ASN         / Certs       / Banners
        │            │            │
        └────────────┼────────────┘
                     ▼
                DNSDumpster
                     │
                     ▼
          Infrastructure Mapping
                     │
                     ▼
                 dig / DNS
                     │
                     ▼
        Verify DNS information
        when scope permits
```

La idea principal durante reconnaissance es:

```text
COLLECT
   ↓
CORRELATE
   ↓
VALIDATE
   ↓
BUILD ATTACK SURFACE
```

y no depender de una única fuente, ya que **Shodan, crt.sh, DNSDumpster, RDAP y DNS pueden contener información de momentos y fuentes diferentes**.

# Guía comparativa de frameworks y estándares para Pentesting

> **Nota de clasificación:** no todos los elementos de esta lista son metodologías de pentesting equivalentes entre sí. **OSSTMM, PTES, NIST SP 800-115 e ISSAF** describen procesos amplios de evaluación; **WSTG y MASTG** son guías técnicas especializadas; **MASVS y PCI DSS** establecen requisitos o criterios de verificación; **MITRE ATT&CK y WASC** son principalmente taxonomías/bases de conocimiento; **CSA** aporta marcos y guías para cloud; y **CBEST** es un framework regulatorio de *Threat-Led Penetration Testing*. Elegirlos y combinarlos según el objetivo suele ser más eficaz que intentar utilizar uno solo.

---

## 1. OSSTMM — Open Source Security Testing Methodology Manual

### Qué es

**OSSTMM**, mantenido por **ISECOM**, es una metodología para medir y evaluar la **seguridad operacional**. Tiene un alcance especialmente amplio porque no se limita a aplicaciones o redes: contempla seguridad de comunicaciones, personas, instalaciones físicas y procesos. ISECOM lo describe como una metodología completa para testing, análisis y medición de seguridad operacional. ([ISECOM][1])

Puede trabajar sobre cinco grandes canales:

* **Human Security**
* **Physical Security**
* **Wireless Communications**
* **Telecommunications**
* **Data Networks**

### Fases

| Fase                | Qué hacer                                                                                                                                                                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Induction**    | Entender el entorno antes de interactuar activamente con él. Revisar postura de seguridad, legislación/políticas aplicables, restricciones, alcance, logística y mecanismos de detección existentes.                                                                 |
| **B. Interaction**  | Determinar qué elementos son visibles y accesibles. Verificar acceso, relaciones de confianza y controles existentes sobre los activos incluidos en alcance.                                                                                                         |
| **C. Inquest**      | Analizar en profundidad procesos, configuraciones, segregación, exposición, propiedades/activos y otros factores que pueden introducir debilidades.                                                                                                                  |
| **D. Intervention** | Evaluar el impacto real de las condiciones encontradas: privilegios, aislamiento, continuidad/supervivencia, alertas, logging y respuesta de los controles. Es la fase de interacción más activa y debe mantenerse estrictamente dentro de las reglas de engagement. |

OSSTMM organiza sus pruebas en módulos que se recorren dentro de estas cuatro fases y enfatiza la medición objetiva de la superficie de ataque y de los controles, en lugar de limitarse a producir una lista de vulnerabilidades. ([ISECOM][2])

### Adecuado para

* Auditorías de infraestructura corporativa.
* Pentest de redes internas y externas.
* Auditorías que incluyan **personas, procesos y seguridad física**.
* Wireless y telecomunicaciones.
* Organizaciones grandes con superficies de ataque heterogéneas.
* Evaluaciones donde se quiera obtener una **medida repetible de seguridad operacional**.
* Auditorías especialmente formales donde interese utilizar el **STAR — Security Test Audit Report**.

### Menos adecuado para

* Un pentest exclusivamente web que requiera casos de prueba detallados.
* Mobile.
* Proyectos pequeños donde la métrica y formalismo de OSSTMM añadan complejidad innecesaria.

### Documentación oficial

* [ISECOM — OSSTMM](https://www.isecom.org/research.html)
* [OSSTMM 3 — PDF oficial](https://www.isecom.org/OSSTMM.3.pdf)
* [STAR — Security Test Audit Report](https://www.isecom.org/STAR.3.pdf)

## 2. OWASP Web Security Testing Guide — WSTG

### Qué es

La **OWASP Web Security Testing Guide (WSTG)** es una guía especializada en la evaluación de seguridad de **aplicaciones y servicios web**. OWASP la mantiene como un conjunto estructurado de buenas prácticas y casos de prueba que pueden referenciarse individualmente mediante identificadores `WSTG-*`. A agosto de 2026, OWASP publica **v4.2 como release versionada** y está desarrollando **v5.0**; OWASP recomienda utilizar referencias versionadas en los informes. ([OWASP][3])

### Fases de seguridad dentro del SDLC

OWASP plantea el testing de seguridad durante todo el ciclo de vida: ([OWASP][4])

| Fase                              | Qué hacer                                                                                                        |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **1. Before Development Begins**  | Definir SDLC de seguridad, políticas, estándares, requisitos y criterios de medición.                            |
| **2. Definition and Design**      | Revisar requisitos de seguridad, arquitectura, diseño y modelos de amenazas antes de implementar.                |
| **3. Development**                | Revisar implementación y código y verificar que el diseño de seguridad se haya materializado correctamente.      |
| **4. Deployment**                 | Realizar configuración segura y pruebas de seguridad/pentesting sobre la aplicación desplegada.                  |
| **5. Maintenance and Operations** | Realizar revisiones periódicas, verificar cambios, nuevas versiones, configuraciones y regresiones de seguridad. |

### Para un pentest web concreto

En una auditoría táctica no suele ejecutarse literalmente todo el SDLC anterior. El trabajo se organiza en torno a las familias de pruebas de WSTG, entre ellas:

1. Information Gathering.
2. Configuration and Deployment Management.
3. Identity Management.
4. Authentication.
5. Authorization.
6. Session Management.
7. Input Validation.
8. Error Handling.
9. Cryptography.
10. Business Logic.
11. Client-side Testing.
12. API Testing.

Por ejemplo, WSTG incluye explícitamente identificación de superficie de ataque, puntos de entrada y caminos de ejecución durante la fase de *Information Gathering*. ([OWASP][5])

### Adecuado para

* Aplicaciones web.
* APIs y servicios web.
* Portales corporativos.
* SaaS.
* E-commerce.
* Pentest web black-box, grey-box o white-box.
* Revisiones de seguridad integradas en SDLC.
* Crear una checklist reproducible para pentests web.

### Punto fuerte

Permite que un finding no sea simplemente:

> “Existe un problema de autenticación”.

sino que el informe pueda indicar exactamente qué caso WSTG se verificó, favoreciendo **trazabilidad, repetibilidad y retesting**.

### Limitación

No pretende cubrir de forma completa:

* Active Directory.
* Redes corporativas.
* Wireless.
* Seguridad física.
* Endpoint.
* Ingeniería social.
* Infraestructura cloud completa.

Debe combinarse con otro marco cuando el alcance excede la aplicación web.

### Documentación oficial

* [OWASP WSTG](https://owasp.org/www-project-web-security-testing-guide/)
* [WSTG Latest](https://owasp.org/www-project-web-security-testing-guide/latest/)
* [OWASP Testing Framework](https://owasp.org/www-project-web-security-testing-guide/latest/3-The_OWASP_Testing_Framework/)

## 3. NIST SP 800-115 — Technical Guide to Information Security Testing and Assessment

### Qué es

**NIST SP 800-115** proporciona recomendaciones para planificar y realizar evaluaciones técnicas de seguridad, analizar resultados y desarrollar estrategias de mitigación. Está orientado tanto al descubrimiento de vulnerabilidades como a comprobar cumplimiento con políticas/requisitos. ([NIST SRI][6])

Tiene un carácter más **formal, organizativo y de assurance** que WSTG o PTES.

### Fases generales de una evaluación NIST

| Fase                  | Qué hacer                                                                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Planning**       | Identificar activos, alcance, objetivos, riesgos, personal, responsabilidades, reglas de engagement, restricciones, recursos, calendario y entregables. |
| **2. Execution**      | Ejecutar las técnicas de evaluación seleccionadas, recopilar evidencias e identificar/validar vulnerabilidades.                                         |
| **3. Post-Execution** | Analizar causas, determinar impacto, priorizar mitigaciones y elaborar el informe final.                                                                |

### Modelo específico de penetration testing

Dentro de SP 800-115, NIST representa un pentest mediante:

| Fase          | Actividades                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Planning**  | Alcance, autorizaciones, reglas, objetivos y coordinación.                                                               |
| **Discovery** | Recopilación de información, identificación de sistemas/servicios y análisis de vulnerabilidades.                        |
| **Attack**    | Validar de manera controlada si las vulnerabilidades identificadas son realmente explotables y qué impacto proporcionan. |
| **Reporting** | Documentación continua del proceso, findings, evidencias, impacto y recomendaciones.                                     |

**Discovery ↔ Attack** puede convertirse en un ciclo: una validación puede revelar nueva información que requiera volver a realizar descubrimiento.

### Adecuado para

* Administraciones públicas.
* Grandes organizaciones.
* Auditorías formales.
* Evaluación de infraestructura.
* Sistemas y redes.
* Evaluación de controles técnicos.
* Validación de políticas.
* Entornos con requisitos de governance/compliance.
* Proyectos donde auditor, cliente y management necesitan un proceso muy controlado y documentado.

### Punto fuerte

Excelente para establecer:

* governance;
* planificación;
* alcance;
* metodología;
* gestión de evidencias;
* reporting;
* mitigación.

### Limitación

No tiene la profundidad de casos técnicos específicos que proporciona:

* WSTG para web;
* MASTG para mobile;
* ATT&CK para adversary emulation.

Por ello es especialmente útil como **framework maestro de gestión**, complementado por guías técnicas.

### Documentación oficial

* [NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final)

## 4. PTES — Penetration Testing Execution Standard

### Qué es

**PTES** es probablemente uno de los modelos más intuitivos para estructurar un **pentest profesional de principio a fin**. Define siete secciones principales que cubren todo el engagement. ([pentest-standard.org][7])

### Fases

| Fase                               | Qué hacer                                                                                                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Pre-engagement Interactions** | Definir objetivos, alcance, contactos, ventanas de prueba, autorizaciones, restricciones, datos sensibles, mecanismos de emergencia y reglas de engagement. |
| **2. Intelligence Gathering**      | Entender la organización y su superficie de exposición mediante información disponible y reconocimiento autorizado.                                         |
| **3. Threat Modeling**             | Identificar activos relevantes, amenazas, atacantes plausibles y rutas de ataque prioritarias.                                                              |
| **4. Vulnerability Analysis**      | Identificar y validar debilidades técnicas o de configuración y descartar falsos positivos.                                                                 |
| **5. Exploitation**                | Comprobar controladamente si una vulnerabilidad permite alcanzar el objetivo definido.                                                                      |
| **6. Post Exploitation**           | Determinar el impacto de un compromiso: nivel de acceso, activos alcanzables y consecuencias para el negocio, siempre dentro del alcance acordado.          |
| **7. Reporting**                   | Elaborar informe ejecutivo y técnico con alcance, evidencias, rutas de ataque, impacto, riesgo y recomendaciones de remediación.                            |

PTES dedica explícitamente secciones a reconnaissance, threat modeling, análisis de vulnerabilidades, exploitation, post-exploitation y reporting. ([pentest-standard.org][8])

### Adecuado para

* Pentest externo.
* Pentest interno.
* Infraestructura.
* Active Directory.
* Redes corporativas.
* Evaluaciones de aplicaciones si se complementa con WSTG.
* Proyectos ofensivos de alcance medio/grande.
* Engagements donde se quiera reproducir una **ruta de compromiso**, no sólo escanear vulnerabilidades.

### Punto fuerte

Es muy sencillo convertir sus fases en el **plan de proyecto real** de una auditoría.

### Limitación

El contenido publicado en el sitio tiene ya bastantes años, por lo que conviene utilizar PTES como estructura metodológica y complementarlo con referencias actuales como WSTG, MASTG, CSA o ATT&CK según la tecnología. El propio sitio mantiene además unas *Technical Guidelines* separadas. ([pentest-standard.org][9])

### Documentación oficial

* [PTES](https://www.pentest-standard.org/index.php/Main_Page)
* [PTES Technical Guidelines](https://www.pentest-standard.org/index.php/PTES_Technical_Guidelines)

## 5. ISSAF — Information Systems Security Assessment Framework

### Qué es

**ISSAF** fue desarrollado originalmente por el **Open Information Systems Security Group (OISSG)** como un framework amplio de evaluación de seguridad de sistemas.

Es importante considerarlo actualmente como un **framework histórico/legacy**. El proyecto conservado en SourceForge se registró en 2003 y muestra como última actualización 2015; el documento ISSAF conocido procede fundamentalmente de la década de 2000. ([SourceForge][10])

Por tanto, resulta útil como **referencia conceptual y catálogo histórico**, pero no sería mi primera elección como metodología principal para un pentest moderno.

### Fases

| Fase                                             | Qué hacer                                                                                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Planning and Preparation**                  | Definir alcance, equipo, calendario, responsables, acuerdos, reglas de engagement y autorizaciones.                                                     |
| **2. Assessment**                                | Realizar el análisis técnico: recopilación de información, mapping, identificación y validación de vulnerabilidades y evaluación controlada de impacto. |
| **3. Reporting, Clean-up and Destroy Artifacts** | Elaborar informes, restaurar el entorno cuando proceda y eliminar de forma controlada los artefactos generados durante la auditoría.                    |

La fase de Assessment del modelo histórico es especialmente extensa y organiza la evaluación mediante diferentes capas y objetivos técnicos. ([untrustednetwork.net][11])

### Adecuado para

Actualmente, principalmente:

* Investigación académica.
* Comparativas de metodologías.
* Sistemas legacy.
* Construcción de checklists históricas.
* Auditorías donde parte del procedimiento corporativo ya esté basado en ISSAF.

### No recomendado como primera elección para

* Aplicaciones web modernas → **WSTG**.
* Mobile → **MASVS + MASTG**.
* Cloud → **CSA + PTES/NIST**.
* Red Team moderno → **PTES/NIST + MITRE ATT&CK**.

### Estado de la documentación

No recomendaría tratar el antiguo dominio de OISSG como una fuente oficial moderna. La distribución histórica del proyecto se conserva en SourceForge.

### Documentación histórica

* [ISSAF — proyecto histórico en SourceForge](https://sourceforge.net/projects/isstf/)

## 6. MITRE ATT&CK

### Qué es

**MITRE ATT&CK no es una metodología de pentesting.**

Es una **base de conocimiento de tácticas y técnicas utilizadas por adversarios**, construida a partir de observaciones del mundo real. ATT&CK modela principalmente:

* **Tactics** → por qué quiere realizar una acción el adversario.
* **Techniques** → cómo intenta conseguir ese objetivo.
* **Sub-techniques** → forma más específica de la técnica.
* **Procedures** → implementaciones observadas de esas técnicas.

ATT&CK mantiene actualmente dominios como **Enterprise, Mobile e ICS**. ([MITRE ATT&CK][12])

### “Fases”

ATT&CK **no establece fases de un proyecto de auditoría** comparables con PTES o NIST.

La matriz representa el comportamiento adversario mediante tácticas. En Enterprise aparecen objetivos como reconnaissance, resource development, initial access, execution, persistence, privilege escalation, defense evasion, credential access, discovery, lateral movement, collection, command and control, exfiltration e impact.

### Flujo recomendado para utilizar ATT&CK en una auditoría

| Paso                                 | Uso de ATT&CK                                                              |
| ------------------------------------ | -------------------------------------------------------------------------- |
| **1. Definir amenaza**               | Identificar los adversarios o comportamientos plausibles para el negocio.  |
| **2. Seleccionar TTPs**              | Identificar las técnicas ATT&CK relevantes para esas amenazas.             |
| **3. Relacionarlas con activos**     | Determinar qué TTPs pueden afectar a los sistemas incluidos en alcance.    |
| **4. Crear escenarios**              | Construir rutas de prueba basadas en comportamientos reales.               |
| **5. Ejecutar con otra metodología** | PTES, NIST, OSSTMM, WSTG, etc. gobiernan el engagement.                    |
| **6. Registrar observabilidad**      | Comprobar qué actividades fueron prevenidas, detectadas o no detectadas.   |
| **7. Mapear findings**               | Relacionar findings/rutas de ataque con técnicas ATT&CK.                   |
| **8. Purple Team**                   | Trabajar con SOC/Blue Team para mejorar telemetría, detección y respuesta. |

MITRE propone ATT&CK específicamente como lenguaje común para **adversary emulation y Red Team**, y también para evaluar capacidades defensivas y decidir qué logging o herramientas hacen falta. ([MITRE ATT&CK][13])

### Cómo combinar ATT&CK con PTES

Una combinación especialmente útil:

| PTES                   | Uso de ATT&CK                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------ |
| Pre-engagement         | Determinar qué comportamiento adversario está permitido simular.                     |
| Intelligence Gathering | Identificar exposición y activos relevantes.                                         |
| Threat Modeling        | **Seleccionar grupos, tácticas y técnicas ATT&CK relevantes.**                       |
| Vulnerability Analysis | Identificar condiciones que permitirían ejecutar dichas TTPs.                        |
| Exploitation           | Validar de manera controlada partes del escenario.                                   |
| Post Exploitation      | Relacionar la ruta alcanzada con tácticas/técnicas ATT&CK.                           |
| Reporting              | Mostrar cobertura ATT&CK, técnicas exitosas, bloqueadas, detectadas y no detectadas. |

Resultado:

```text
PTES = cómo organizar el pentest
ATT&CK = qué comportamiento adversario queremos representar
```

### Cómo combinar ATT&CK con NIST SP 800-115

```text
NIST
│
├── Planning
│   └── Selección de amenazas/TTPs ATT&CK
│
├── Execution
│   └── Simulación controlada de las TTPs seleccionadas
│
└── Post-Execution
    ├── Findings técnicos
    ├── Cobertura ATT&CK
    ├── Controles preventivos
    ├── Detecciones
    └── Plan de mejora
```

### Cómo combinar ATT&CK con WSTG

WSTG puede descubrir, por ejemplo:

```text
Debilidad de aplicación
        ↓
Impacto técnico
        ↓
Posible punto de entrada
        ↓
Técnica(s) ATT&CK asociada(s)
        ↓
Ruta de ataque empresarial
        ↓
Controles/detecciones necesarios
```

Así se evita terminar el análisis en:

> “La web contiene la vulnerabilidad X”.

y se puede responder también:

> “¿Cómo puede utilizarse esta debilidad dentro de un ataque contra la organización?”

### Cómo combinar ATT&CK con OSSTMM

OSSTMM puede dar cobertura amplia a:

* red;
* wireless;
* telecomunicaciones;
* personas;
* instalaciones.

ATT&CK complementa esta evaluación proporcionando un **modelo del comportamiento adversario digital** y facilita convertir findings aislados en rutas de ataque.

### Adecuado para

* Red Team.
* Purple Team.
* Threat-Led Penetration Testing.
* Adversary Emulation.
* Validación SOC/SIEM/EDR.
* Detection Engineering.
* Evaluación de cobertura defensiva.
* Ejercicios basados en Threat Intelligence.
* Enterprise, cloud, mobile e ICS según la matriz correspondiente.

### Documentación oficial

* [MITRE ATT&CK](https://attack.mitre.org/)
* [ATT&CK Resources](https://attack.mitre.org/resources/)
* [Adversary Emulation and Red Teaming](https://attack.mitre.org/resources/get-started/adversary-emulation-and-red-teaming/)
* [Assessment and Engineering](https://attack.mitre.org/resources/get-started/assessment-and-engineering/)
* [Detections and Analytics](https://attack.mitre.org/resources/get-started/detections-and-analytics/)

## 7. Web Application Security Consortium — WASC

### Qué es

**WASC Threat Classification** es principalmente una **taxonomía de amenazas y debilidades de aplicaciones web**, no una metodología completa de pentesting.

WASC Threat Classification v2.0 pretende clasificar y organizar las debilidades y ataques que pueden comprometer un sitio web, sus datos o sus usuarios. La versión 2.0 publicada corresponde a 2010, por lo que debe considerarse fundamentalmente una referencia **legacy** frente a proyectos OWASP mantenidos activamente. ([WebAppSec Projects][14])

### Fases

No define un ciclo de engagement equivalente a PTES.

Un uso razonable sería:

| Paso             | Qué hacer                                                                  |
| ---------------- | -------------------------------------------------------------------------- |
| **1. Scope**     | Identificar aplicaciones y componentes web.                                |
| **2. Test**      | Ejecutar pruebas con WSTG u otra metodología.                              |
| **3. Classify**  | Clasificar los findings utilizando la taxonomía WASC cuando sea necesario. |
| **4. Correlate** | Relacionar categorías entre herramientas, scanners e informes históricos.  |
| **5. Report**    | Utilizar la clasificación como metadato adicional del finding.             |

### Adecuado para

* Informes o herramientas antiguas que todavía utilizan IDs WASC.
* Normalización de findings.
* Comparativas históricas.
* Evaluación de scanners/WAFs.
* Organizaciones con taxonomías corporativas heredadas basadas en WASC.

### Recomendación actual

Para una auditoría nueva:

```text
WSTG → metodología técnica principal
WASC → taxonomía complementaria si existe necesidad de compatibilidad
```

### Documentación

* [WASC Threat Classification v2.0](https://projects.webappsec.org/w/page/13246978/Threat%20Classification)
* [WASC Threat Classification v2.0 — PDF](https://projects.webappsec.org/f/WASC-TC-v2_0.pdf)

## 8. Cloud Security Alliance — CSA

### Qué es

**CSA no es una única metodología de pentesting**. Cloud Security Alliance mantiene diferentes estándares, matrices y guías de seguridad cloud.

Para pentesting destacan especialmente:

1. **Cloud Controls Matrix (CCM)** → baseline de controles cloud.
2. **Cloud Penetration Testing Playbook** → guía específica para penetration testing de sistemas y aplicaciones alojados en public cloud.

La CCM contiene **197 objetivos de control agrupados en 17 dominios** y está diseñada para realizar evaluaciones sistemáticas de implementaciones cloud y clarificar responsabilidades dentro de la cadena de suministro cloud. ([Cloud Security Alliance][15])

El Cloud Penetration Testing Playbook se orienta específicamente a sistemas y servicios controlados por el cliente en entornos de nube pública y no presupone que la infraestructura gestionada exclusivamente por el proveedor cloud sea automáticamente parte del alcance. ([Cloud Security Alliance][16])

### Flujo recomendado para una auditoría cloud

| Fase                                 | Qué hacer                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Scope & Shared Responsibility** | Identificar proveedor, servicios, tenant/account/subscriptions/projects, responsabilidades CSP/cliente y restricciones del proveedor. |
| **2. Control Baseline**              | Seleccionar controles relevantes de CSA CCM.                                                                                          |
| **3. Architecture Review**           | Analizar IAM, red, almacenamiento, secretos, logging, workloads, APIs, CI/CD y servicios gestionados.                                 |
| **4. Technical Testing**             | Aplicar el Cloud Penetration Testing Playbook y las pruebas específicas autorizadas.                                                  |
| **5. Attack-path Analysis**          | Evaluar cómo una configuración o identidad puede encadenarse hacia activos críticos.                                                  |
| **6. ATT&CK Mapping**                | Opcionalmente mapear escenarios a ATT&CK Enterprise/cloud.                                                                            |
| **7. Reporting**                     | Findings técnicos + controles CCM afectados + impacto + remediación.                                                                  |

> Estas fases constituyen una forma práctica de integrar las herramientas de CSA; **CCM no define por sí sola un lifecycle de pentesting**.

### Adecuado para

* AWS.
* Microsoft Azure.
* Google Cloud Platform.
* SaaS/PaaS/IaaS.
* Cloud-native.
* Kubernetes y workloads cloud, combinado con referencias específicas.
* Revisiones IAM.
* Auditorías de configuración.
* Revisiones de arquitectura.
* Compliance cloud.

### Combinación recomendada

```text
PTES o NIST
    ↓
gestión del engagement

CSA CCM
    ↓
controles cloud que deben verificarse

CSA Cloud Penetration Testing Playbook
    ↓
testing cloud

MITRE ATT&CK
    ↓
rutas/TTPs de adversario

WSTG
    ↓
aplicaciones y APIs desplegadas en cloud
```

### Documentación oficial

* [Cloud Security Alliance](https://cloudsecurityalliance.org/)
* [CSA Cloud Controls Matrix](https://cloudsecurityalliance.org/research/cloud-controls-matrix)
* [CSA Cloud Penetration Testing Playbook](https://cloudsecurityalliance.org/artifacts/cloud-penetration-testing-playbook)

## 9. OWASP Mobile Application Security Verification Standard — MASVS

### Qué es

**MASVS es un estándar de verificación de seguridad para aplicaciones móviles**, no una metodología de pentesting.

Define **qué propiedades de seguridad debería cumplir una aplicación**, mientras que MASTG explica **cómo verificarlas técnicamente**. OWASP lo plantea como estándar para arquitectos, desarrolladores y security testers y también como baseline para procesos de verificación o adquisición de aplicaciones móviles. ([OWASP Mobile Application Security][17])

### Grupos de controles actuales

| Grupo                | Evalúa                                                           |
| -------------------- | ---------------------------------------------------------------- |
| **MASVS-STORAGE**    | Protección de datos almacenados.                                 |
| **MASVS-CRYPTO**     | Uso correcto de criptografía.                                    |
| **MASVS-AUTH**       | Autenticación y autorización.                                    |
| **MASVS-NETWORK**    | Protección de comunicaciones de red.                             |
| **MASVS-PLATFORM**   | Interacción segura con Android/iOS y otras aplicaciones.         |
| **MASVS-CODE**       | Buenas prácticas de seguridad del código y plataforma soportada. |
| **MASVS-RESILIENCE** | Resistencia frente a manipulación y reverse engineering.         |
| **MASVS-PRIVACY**    | Protección de privacidad y datos personales.                     |

OWASP mantiene estos grupos como estructura actual del estándar. ([OWASP Mobile Application Security][17])

### Fases

MASVS no define fases de pentest.

Un workflow habitual sería:

| Paso                | Qué hacer                                                                |
| ------------------- | ------------------------------------------------------------------------ |
| **1. Scope**        | Determinar plataforma, versión, componentes y datos sensibles.           |
| **2. Requirements** | Seleccionar controles MASVS aplicables.                                  |
| **3. Threat Model** | Identificar amenazas específicas de la aplicación.                       |
| **4. Test Mapping** | Asociar controles MASVS con tests de MASTG.                              |
| **5. Verification** | Ejecutar análisis estático, dinámico y otras verificaciones pertinentes. |
| **6. Evidence**     | Documentar evidencias por control.                                       |
| **7. Report**       | Indicar controles compliant/non-compliant y findings correspondientes.   |

### Adecuado para

* Android.
* iOS.
* Apps bancarias.
* Wallets.
* Apps sanitarias.
* Aplicaciones que procesan PII.
* Aplicaciones empresariales.
* Definir requisitos en SDLC.
* Procurement de aplicaciones.
* Pentest y certificación interna.

### Documentación oficial

* [OWASP MASVS](https://mas.owasp.org/MASVS/)
* [Using the MASVS](https://mas.owasp.org/MASVS/03-Using_the_MASVS/)

## 10. OWASP Mobile Application Security Testing Guide — MASTG

### Qué es

**MASTG** es la guía técnica que complementa MASVS.

OWASP la define como un **manual completo para mobile application security testing y reverse engineering** y sus pruebas permiten verificar los controles de MASVS. ([OWASP Mobile Application Security][18])

La relación conceptual es:

```text
MASVS
¿Qué seguridad debería tener?
        ↓
MASTG
¿Cómo compruebo técnicamente que la tiene?
```

### Flujo típico de auditoría

MASTG no obliga a utilizar un lifecycle único de proyecto, pero puede estructurarse como:

| Fase                             | Qué hacer                                                                                                 |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **1. Preparation**               | Obtener aplicaciones, builds, cuentas, dispositivos/emuladores, arquitectura y alcance.                   |
| **2. Mapping**                   | Determinar controles MASVS que se comprobarán.                                                            |
| **3. Static Analysis**           | Examinar código, binarios, configuración, manifiestos, librerías y artefactos sin ejecutar la aplicación. |
| **4. Dynamic Analysis**          | Observar comportamiento de la app en ejecución y sus interacciones con sistema, red y almacenamiento.     |
| **5. Platform-specific Testing** | Realizar tests específicos de Android/iOS.                                                                |
| **6. Resilience Assessment**     | Cuando aplique, evaluar controles contra manipulación/reverse engineering.                                |
| **7. MASVS Mapping & Reporting** | Asociar resultados con MASVS y producir evidencias reproducibles.                                         |

MASTG diferencia, entre otras técnicas, entre análisis estático y dinámico, e incluye tests, técnicas, demos, herramientas y conocimientos específicos de plataforma. ([OWASP Mobile Application Security][19])

### Adecuado para

* Pentest Android.
* Pentest iOS.
* Reverse engineering autorizado.
* Secure SDLC mobile.
* Automatización de security testing.
* Evaluaciones basadas en MASVS.
* Retesting de aplicaciones.

### Combinación recomendada

```text
PTES
 └── gestión global del engagement

MASVS
 └── requisitos de seguridad

MASTG
 └── pruebas técnicas

MITRE ATT&CK Mobile
 └── contexto adversario
```

### Documentación oficial

* [OWASP MASTG](https://mas.owasp.org/MASTG/)
* [OWASP MAS Project](https://mas.owasp.org/)

## 11. PCI DSS Penetration Testing Guidance

### Qué es

La **PCI DSS Penetration Testing Guidance** proporciona orientación específica sobre cómo diseñar y documentar pentests relacionados con el **Cardholder Data Environment (CDE)**.

El documento de guidance enlazado es de **septiembre de 2017** y se redactó sobre PCI DSS v3.x. Define explícitamente tres grandes partes del pentest: **pre-engagement, engagement y post-engagement**. ([PCI Security Standards Council][20])

> **Importante:** esta guía sigue siendo útil metodológicamente, pero no debe utilizarse como fuente única para determinar los requisitos PCI actuales. En 2026 el PCI SSC publica **PCI DSS v4.0.1** en su Document Library, mientras que el guidance de 2017 utiliza numeración y requisitos de PCI DSS v3.x. ([PCI Security Standards Council][21])

### Fases

| Fase                   | Qué hacer                                                                                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Pre-engagement**  | Identificar CDE y sistemas críticos, confirmar alcance, documentación, segmentación, perspectivas de testing, restricciones, reglas de engagement y criterios de éxito. |
| **2. Engagement**      | Ejecutar las pruebas internas/externas correspondientes sobre red y aplicaciones y verificar segmentación cuando forme parte del diseño del CDE.                        |
| **3. Post-engagement** | Documentar resultados, remediar, realizar retesting cuando corresponda y actualizar el resultado final.                                                                 |

La guía enfatiza además:

* correcta definición del CDE;
* sistemas críticos;
* testing interno y externo;
* network-layer testing;
* application-layer testing;
* validación de segmentación;
* cualificación del pentester;
* metodología reproducible;
* reglas de engagement;
* reporting.

([PCI Security Standards Council][20])

### Adecuado para

* Comercios que procesan tarjetas.
* PSPs.
* Payment gateways.
* Procesadores de pago.
* Entornos e-commerce.
* Infraestructura relacionada con el CDE.
* Proyectos que requieren evidencia para PCI DSS.

### Recomendación de combinación

PCI dice **qué debe cubrirse por necesidad de compliance**, pero no sustituye una metodología técnica profunda.

Una buena combinación:

```text
PCI DSS
    ↓
requisitos + scope CDE

PTES / NIST
    ↓
gestión del pentest

WSTG
    ↓
aplicación web / API

OSSTMM o PTES
    ↓
infraestructura

CSA
    ↓
si el CDE está en cloud

MASVS + MASTG
    ↓
si existe aplicación mobile de pagos
```

El estándar PCI DSS actual sigue requiriendo que se realicen regularmente pruebas de penetración internas y externas y que las debilidades explotables se corrijan; el detalle vigente debe validarse siempre contra PCI DSS v4.0.1 y documentación actual del Council. ([PCI Security Standards Council][22])

### Documentación oficial

* [PCI DSS Penetration Testing Guidance v1.1](https://listings.pcisecuritystandards.org/documents/Penetration-Testing-Guidance-v1_1.pdf)
* [PCI SSC Document Library — documentación vigente](https://www.pcisecuritystandards.org/document_library/)
* [PCI DSS](https://www.pcisecuritystandards.org/standards/pci-dss/)

## 12. CBEST

### Qué es

**CBEST** es el framework británico de **intelligence-led penetration testing / Threat-Led Penetration Testing (TLPT)** utilizado por Bank of England/PRA/FCA para evaluar la resiliencia de entidades financieras y Financial Market Infrastructures.

No se trata de un pentest de vulnerabilidades convencional. Busca simular comportamientos de actores de amenaza relevantes contra los **Important Business Services (IBS)** de la organización y evaluar tanto las defensas como capacidades de Threat Intelligence y Detection & Response. ([Banco de Inglaterra][23])

### Fases oficiales

| Fase                       | Qué hacer                                                                                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Initiation**          | Lanzar el CBEST, crear governance/Control Group, establecer alcance, identificar IBS y sistemas críticos y contratar proveedores acreditados de Threat Intelligence y Penetration Testing.      |
| **2. Threat Intelligence** | Construir inteligencia específica de la organización, identificar actores relevantes, superficie de targeting y escenarios probables; convertirlos progresivamente en un Penetration Test Plan. |
| **3. Penetration Testing** | Planificar y ejecutar un pentest intelligence-led contra sistemas/servicios que soportan los IBS. También se evalúan las capacidades de Detection & Response.                                   |
| **4. Closure**             | Finalizar el remediation plan, realizar debriefs y permitir que el regulador supervise la remediación.                                                                                          |

Estas son las cuatro fases definidas oficialmente en la Implementation Guide 2024. ([Banco de Inglaterra][23])

### Relación especialmente interesante con MITRE ATT&CK

CBEST indica expresamente que el **Penetration Test Plan** debe incluir el attack plan utilizando metodologías o frameworks establecidos y cita como ejemplos **MITRE ATT&CK y Cyber Kill Chain**. ([Banco de Inglaterra][23])

Por tanto:

```text
Threat Intelligence
        ↓
Threat Actor
        ↓
Threat Scenarios
        ↓
MITRE ATT&CK TTPs
        ↓
Penetration Test Plan
        ↓
Execution
        ↓
Detection & Response Assessment
        ↓
Remediation
```

Es uno de los ejemplos más claros de cómo **ATT&CK debe complementar una metodología en vez de reemplazarla**.

### Adecuado para

* Bancos sistémicamente importantes.
* Aseguradoras/entidades financieras cuando entren en el ámbito correspondiente.
* Financial Market Infrastructures.
* Grandes entidades reguladas.
* Threat-Led Penetration Testing.
* Red Team basado en inteligencia real.
* Evaluación avanzada de SOC/Blue Team.
* Cyber resilience.

CBEST puede ser requerido por el regulador, solicitado voluntariamente por una firma con acuerdo regulatorio o desencadenarse como parte de actividades posteriores a determinados incidentes. ([Banco de Inglaterra][23])

### No adecuado para

* Pentest puntual de una web.
* SME que necesita un vulnerability assessment.
* Auditoría rápida de infraestructura.
* Proyecto sin capacidad de Threat Intelligence/Red Team madura.

Es un ejercicio considerablemente más complejo que un pentest tradicional; la guía indica como referencia que un CBEST completo suele durar aproximadamente **9–12 meses**, aunque la duración debe adaptarse al alcance. ([Banco de Inglaterra][23])

### Documentación oficial

* [Bank of England — CBEST Threat Intelligence-Led Assessments Implementation Guide](https://www.bankofengland.co.uk/financial-stability/operational-resilience-of-the-financial-sector/cbest-threat-intelligence-led-assessments-implementation-guide)
